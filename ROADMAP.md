# AsmEditor — план развития

Все пункты прежних списков реализованы (см. README). Ниже — что проверено, что сделано с оговорками и что
осталось сделать людям, а не коду.

## Проверено

- **Тесты** (`build.bat test`, 568 проверок): сквозные тесты отладчика на 64- и 32-битной (WOW64) программе —
  условия, точки останова на данные (в том числе в другом потоке), стек вызовов (через `qsort` в ucrtbase — по
  `.pdata`), logpoints, шаг назад, профилировщик; анализатор кода и быстрые исправления; аргументы `call`; условия
  переходов; разбор gdb/MI; 13 учебных задач решаются эталонными решениями, уроки и экспорт результатов;
  ассоциация файлов (в тестовом ключе реестра); каждый текст интерфейса и весь справочник есть на английском.
- **Автотест интерфейса** (`build.bat uitest`): окно открывает проект, ставит точку останова, отлаживает, шагает,
  делает шаг назад, показывает вкладку «Флаги», профилирует — через WM_COMMAND, со снимками экрана.

## Сделано с оговорками

- **Отладка Linux-программ через gdb/MI** написана, но не запускалась: на машине разработки нет дистрибутива WSL.
  Проверены только разбор ответов gdb и перевод выражений и путей. Для проверки: `wsl --install -d Ubuntu`,
  `sudo apt install gdb nasm`, профиль платформы «Linux (WSL)» и F5. Шаг назад и профилировщик в WSL не работают.
- **CI** (`build.yml`) работает на GitHub (https://github.com/Anready/AsmEditor) вручную и на pull request (не на каждый push): сборка, все тесты, автотест
  интерфейса на раннере, портативный zip и установщик Inno Setup — артефакты сборки. **Релиз** (`release.yml`) по тегу
  `v*` собирает, тестирует и публикует релиз; заметки к нему — раздел версии из `CHANGELOG.md`.
- **Снимки для сравнения** в автотесте интерфейса (`tests/ui-baseline`) пока не заведены: их нужно взять из артефакта
  `ui-test` сборки в CI (скачивается после входа на GitHub; снимки с экрана с другим масштабом отличаются).
- **Подпись кода** в релизе выполняется, только если заданы секреты `SIGNING_CERT` и `SIGNING_PASSWORD`.
- **Профилировщик** трассирует каждую инструкцию через Debug API (~0,3 мс на инструкцию): после 1 млн инструкций
  программа работает дальше без подсчёта. Время у строк включает накладные расходы отладчика.
- **Шаг назад** восстанавливает регистры, секции данных, стек и кучу; файлы и вывод — нет.
- **Стек вызовов** у NASM-кода без таблиц раскрутки по-прежнему строится по адресам возврата в стеке.
- **Проверка обновлений** читает страницы nasm.us и scintilla.org; при смене их разметки перестанет находить версию.

### Сделано из второго списка
- «Объясни строку»: при остановке у текущей строки — что сделает инструкция с текущими значениями.
- Профилировщик по таймеру (Запуск → «Профилировать по таймеру»): замер раз в 1 мс, время printf и WinAPI — строке
  вызова (раскрутка по `.pdata`); в отличие от пошагового не считает число выполнений.
- Анализатор: значение rcx, rdx, r8–r11 читается после `call` внешней функции, которая могла его испортить.
- Подсказки аргументов своих функций по комментарию над меткой (`; rcx = a, rdx = b`).
- Форматирование при сохранении (настройка), портативный режим (`portable.txt` или папка `settings` рядом с exe;
  портативный zip так и собирается).
- Задачи: обязательные и запрещённые инструкции, требование рекурсии, подсказки по уровням (Ctrl+Shift+H),
  условия задач на английском, сводка по группе из нескольких CSV.
- 32-битные Linux-программы (`-f elf32`, `gcc -m32`; в WSL нужен `gcc-multilib`) — не проверено, как и весь WSL.
- Справка по F1: страница с быстрым стартом, примером, выражениями отладчика и всеми командами.
- Шаг назад восстанавливает и кучу (сегменты куч из PEB, до 8 МБ на остановку).
- Наблюдение: области памяти (`msg, 32`) и структуры (`p as Point` по `struc … endstruc` проекта).
- Подключение к запущенному процессу (Запуск → «Подключиться к процессу…»); «Стоп» отключает отладчик.
- Переименование `%%меток` макроса — только внутри своего `%macro`; поиск использований `%define`, `%assign`,
  `%macro` и `%%меток` покрыт тестом (само окно переименования проверено только сборкой).
- Встроенный дизассемблер вместо ndisasm (вкладка «Код»): целочисленные инструкции, частые SSE/SSE2, префиксы,
  64 и 32 бит. Тест: ~230 инструкций проходят круг «байты → текст → NASM → байты → тот же текст». Остальное
  (AVX-512, редкие системные и SSE3+) показывается как `db 0x..`.

- Дизассемблер знает и x87, и частые AVX/AVX2/FMA (VEX); в круговом тесте около 330 инструкций.
- Предел числа инструкций в задачах (`fib`, `factorial`): решение прогоняется под пошаговым профилировщиком на
  последнем тесте.
- Задачи преподавателя из текстового файла (Запуск → «Загрузить задачи преподавателя…», формат — в README).
- Заготовки задач полностью на английском в английском интерфейсе.
- Тест отладки программы с окном: точка останова в оконной процедуре, стек через user32 до `DispatchMessageA`.

- Автообновление из релизов GitHub. Проверено целиком на портативной копии с подставным релизом
  (`ASMEDITOR_UPDATE_FEED` → локальный JSON): диалог, загрузка, SHA-256, замена exe, перезапуск, уборка `.old`;
  запрос к GitHub API и загрузка по HTTPS — юнит-тестами. Обновление установленной копии через установщик
  (`/SILENT /CLOSEAPPLICATIONS`) ещё не запускалось: нужен второй релиз.

### Отладчик уровня x64dbg

Сейчас отладчик сильный для своего кода с исходниками и слабый для всего остального: чужих exe и DLL,
системного кода, программ без символов. Цель — чтобы в нём можно было разобрать любой процесс, как в x64dbg, не
потеряв того, что есть (исходник, пояснения, шаг назад). Этапы по порядку пользы; каждый — со сквозными тестами
в `tests.cpp`, как у нынешнего отладчика.

**1. Окно CPU: дизассемблер любого адреса, а не только своего кода**
- Вкладка «Код» становится полноценным видом CPU: прокрутка вверх и вниз по произвольной памяти (вверх — с
  повторной синхронизацией по границам инструкций), переход по адресу и выражению (Ctrl+G), «следовать» за
  `jmp`/`call`/операндом в памяти, история переходов (назад и вперёд).
- Стрелки переходов слева от инструкций, подсветка цели, отметка «переход будет / не будет» на текущей.
- Имена вместо адресов: `call [rel __imp_printf]` → `call ucrtbase.printf`, метки модулей, строки у `lea`
  на данные.
- Точки останова, «выполнить до сюда» и «перенести выполнение сюда» прямо в этом окне, без исходника.
- Дизассемблер — полный набор инструкций (AVX-512/EVEX, все SSE3+, системные). Вместо дописывания своего
  разумно взять Zydis (MIT, без зависимостей, кодирует и декодирует) и оставить свой для подписей NASM.

**2. Символы чужого кода**
- DbgHelp с сервером символов: `srv*<кэш>*https://msdl.microsoft.com/download/symbols` (настройка, кэш в папке
  настроек) — имена функций ntdll, kernel32, ucrtbase в стеке вызовов, дизассемблере и выражениях.
- Загрузка символов для каждого модуля по `LOAD_DLL_DEBUG_EVENT` (сейчас — только для своего exe), выгрузка
  по `UNLOAD_DLL_DEBUG_EVENT`.
- Экспорты и импорты из PE, когда PDB нет; окно «Символы»: модули → функции, поиск, переход.
- Выражения: `kernel32.CreateFileW`, `module + 0x1234`, `[rsp+8]` в контексте чужого модуля.

**3. Модули, потоки, карта памяти**
- Вкладка «Модули»: база, размер, путь, загружены ли символы, точка входа; перейти, поставить точку останова на
  экспорт.
- Вкладка «Потоки»: id, адрес старта, текущий rip, приоритет, приостановлен ли; переключение потока (регистры,
  стек вызовов и CPU показывают выбранный), приостановить и возобновить, TEB.
- Вкладка «Карта памяти» (`VirtualQueryEx` по всему адресному пространству): регионы, защита, тип (образ,
  отображение, частная), владелец (модуль и секция, стек потока, куча, PEB/TEB); изменить защиту, сохранить
  регион в файл.

**4. Точки останова всех видов**
- Точки останова на память (страницы `PAGE_GUARD` или `PAGE_NOACCESS`): чтение, запись, выполнение любого
  размера, а не только 1–8 байт DR0–DR3; аккуратное восстановление защиты и пошаговый проход через страницу.
- Аппаратные на выполнение (DR с RW=00), на чтение/запись (уже есть) — с выбором потока или во всех.
- Останов на загрузку DLL, на создание потока, на точку входа модуля, на системную точку останова и
  на `TLS`-callback.
- Исключения: список кодов (`0xC0000005`, `0x80000003`, C++ `0xE06D7363`…) с выбором «останавливаться на первом
  шансе / на втором / передавать программе»; цепочка обработчиков (SEH на x86, `.pdata`/`UNWIND_INFO` на x64)
  во вкладке.
- Счётчик срабатываний и «одноразовые» точки у каждой точки останова; все точки — в одном списке с
  включением, условием, логом и командой при срабатывании.

**5. Регистры полностью**
- YMM (AVX, через `GetThreadContext` с `CONTEXT_XSTATE` / `InitializeContext2` + `LocateXStateFeature`) и ZMM/k0–k7
  (AVX-512), представление как байты, word, dword, qword, float, double, по выбору.
- x87: ST0–ST7 как числа с расширенной точностью, слова управления, состояния и тегов; MXCSR с расшифровкой
  флагов; сегментные регистры и базы FS/GS; DR0–DR7.
- Изменение любого из них двойным щелчком (сейчас — только регистры общего назначения и флаги).

**6. Память и поиск**
- Несколько панелей памяти, вид «как в x64dbg»: адрес, hex, ASCII/UTF-16; выделение, копирование,
  изменение, заполнение.
- Поиск: байтовый шаблон с `??` в регионе, модуле или всей памяти; строки ASCII и UTF-16; константа.
- «Ссылки на»: какие инструкции модуля обращаются к адресу, строке, константе; все межмодульные вызовы модуля.
- Стек как отдельная панель: значения с подписью (адрес возврата в `модуль.функция+N`, указатель на строку).

**7. Изменение программы (патчи)**
- Ассемблирование в месте (Пробел в CPU): строка NASM → байты через встроенный NASM или кодировщик Zydis;
  заполнение NOP остатка.
- Список патчей с откатом; сохранение изменённого exe/DLL на диск (секции образа → смещения в файле).
- Дамп процесса из памяти с восстановлением таблицы импорта — нужен для упакованных программ (у x64dbg это
  плагин Scylla; можно поставить его как внешний инструмент).

**8. Трассировка и анализ**
- Трассировка с условием остановки («шагать, пока `rax == 0`», «до возврата», «до выхода из модуля»), запись
  трассы в файл (адрес, инструкция, изменённые регистры) и просмотр с поиском — расширение нынешнего шага назад.
- Покрытие: какие инструкции модуля выполнились (подсветка в CPU) — основа уже есть в профилировщике.
- Анализ модуля: границы функций (по `.pdata`, точкам входа и `call`-целям), перекрёстные ссылки, циклы;
  граф функции (блоки и переходы) как отдельный вид.
- База пометок: комментарии, метки, закладки к адресам — сохраняются по модулю и смещению между запусками.

**9. Командная строка и сценарии**
- Строка команд под CPU: `bp`, `bpm`, `g`, `t`, `p`, `d`, `u`, `r rax=5`, `log` — как в x64dbg/WinDbg; та же
  разборка выражений, что у наблюдения.
- Сценарии (последовательность команд из файла, с условиями и метками) — для повторяемых сеансов.

**10. Прочее, что ждут от «настоящего» отладчика**
- Отладка с правами администратора (перезапуск AsmEditor с UAC), подключение к службам — с предупреждением.
- Отладка дочерних процессов (`DEBUG_PROCESS` вместо `DEBUG_ONLY_THIS_PROCESS`), переключение между процессами.
- Открытие минидампа (`.dmp`) только для просмотра: модули, потоки, регистры, память, стек.
- Окна «Дескрипторы» и «Окна» процесса — второстепенно.
- Не делать: обход антиотладки (ScyllaHide) и плагины-SDK — у x64dbg это экосистема, а не ядро; цель здесь —
  разбор обычных программ.

**Что останется лучше, чем у x64dbg**: исходник NASM рядом с машинным кодом, пояснение строки и флагов,
анимация стека, шаг назад, профилировщик по строкам, gdb для Linux в тех же панелях. Самые трудоёмкие этапы —
1 (полный ISA и вид CPU), 4 (точки на память без поломки программы) и 8 (анализ модуля); самые полезные для
своего кода сразу — 2, 3 и 5.
